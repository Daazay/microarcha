# Каталог микросервисов

Пути ниже обозначают предлагаемые внутренние REST API. Внешний доступ проходит через API Gateway; доступ к административным и служебным операциям ограничен ролями. Для всех команд с побочными эффектами применяются ключ идемпотентности и проверка прав. События передаются через Kafka, схемы версионируются.

## Schedule Service

- **Responsibility / Owned Data:** управление расписанием и схемами составов; Station, Route, Train, Carriage, Seat, Trip.
- **API:** `GET /trips/{id}`, `GET /trips/{id}/seat-map`, `PUT /trips/{id}` (административный, с ожидаемой версией).
- **Dependencies:** брокер событий; адаптер источника расписания при необходимости.
- **Communication:** REST; публикация `TripPublished`, `TripChanged`, `TripCancelled` с версией рейса.
- **Scalability:** реплики приложения, кеш и реплики чтения. Изменения одного рейса сериализуются. Изменение состава с проданными билетами требует бизнес-процесса пересадки/возврата, а не перезаписи схемы мест.

## Search Service

- **Responsibility / Owned Data:** поиск по станциям, дате и фильтрам; SearchDocument.
- **API:** `GET /journeys?from=...&to=...&date=...`.
- **Dependencies:** события Schedule, поисковый индекс.
- **Communication:** REST для выдачи, Kafka для обновления проекции. Цена в выдаче, если добавлена, носит справочный характер; окончательная цена фиксируется Booking.
- **Scalability:** горизонтальные реплики, кеш популярных запросов, секционирование индекса по дате/направлению. Поиск не обращается к каждому доменному сервису на каждый запрос. Точная доступность проверяется отдельно при выборе места.

## Inventory Service

- **Responsibility / Owned Data:** исключение двойной продажи; TripSeat, Hold с TTL, Allocation. Локальная проекция схемы рейса поступает из Schedule.
- **API:** `GET /trips/{id}/availability?from=...&to=...`, `POST /holds`, `POST /holds/{id}/confirm`, `POST /holds/{id}/release`, `POST /allocations/{id}/release`, `GET /holds/{id}`.
- **Dependencies:** события Schedule; транзакционная БД Inventory.
- **Communication:** REST-команды от Booking; события `HoldExpired`, `AllocationConfirmed`, `AllocationReleased`.
- **Scalability:** секционирование по TripId; транзакции внутри одного рейса. Нельзя решать конфликт продажи только кешем или распределенным локом без проверки в БД.

Маршрут A–B–C делится на элементарные сегменты A–B и B–C. Одно место можно продать двум пассажирам на непересекающиеся сегменты; продажа A–C конфликтует с обоими. Удержание всех запрошенных сегментов выполняется одной транзакцией с блокировкой соответствующих строк в фиксированном порядке и проверкой занятости. Это позволяет атомарно удерживать несколько мест одного рейса. Подтверждение и истечение TTL используют те же строки и условные переходы состояния, поэтому победить может только один переход. Бронирование нескольких рейсов атомарно не поддерживается: для него нужна отдельная сага.

## Booking Service

- **Responsibility / Owned Data:** покупка, билет, тариф и возврат; Booking, Ticket, FareRule, PriceQuote, RefundRequest, SagaState. Итоговая цена и версия тарифа фиксируются до оплаты.
- **API:** `POST /bookings`, `GET /bookings/{id}`, `GET /tickets/{id}`, `POST /tickets/{id}/refund-requests`.
- **Dependencies:** Schedule (валидация рейса), Passenger (снимок данных), Inventory (места), Payment (деньги).
- **Communication:** REST для команд и чтения; Kafka для результатов платежей и мест, публикация `TicketIssued`, `TicketRefunded`, `BookingFailed`. Сага хранится в БД, таймеры переживают перезапуск процесса.
- **Scalability:** stateless API и фоновые обработчики, распределение по BookingId. Конкурирующие изменения заказа защищены версией/блокировкой. Выдача билета разрешается только после подтвержденной оплаты и закрепления места.

## Payment Service

- **Responsibility / Owned Data:** учет денежных операций; Payment, PaymentAttempt, Refund, ProviderEvent. Реквизиты банковских карт не хранятся, используются токены/платежная страница провайдера.
- **API:** `POST /payments`, `GET /payments/{id}`, `POST /payments/{id}/refunds`, `POST /provider/webhooks`.
- **Dependencies:** внешний платежный провайдер.
- **Communication:** REST, подписанные webhook провайдера; Kafka: `PaymentSucceeded`, `PaymentFailed`, `RefundSucceeded`, `RefundFailed`. Тайм-аут запроса не означает отказ платежа: статус уточняется у провайдера.
- **Scalability:** реплики и очереди с учетом лимитов провайдера; уникальные ключи операций и дедупликация webhook. Периодическая сверка выявляет пропущенные подтверждения.

## Passenger Service

- **Responsibility / Owned Data:** профили пассажиров, документы, контакты и согласия.
- **API:** `POST /passengers`, `GET /passengers/{id}`, `PATCH /passengers/{id}`.
- **Dependencies:** провайдер идентификации для проверки пользователя.
- **Communication:** REST; персональные данные не распространяются массовыми событиями. Booking получает только необходимые данные с проверкой доступа.
- **Scalability:** горизонтальные реплики, распределение по PassengerId. Шифрование, разграничение доступа и маскирование логов обязательны для защиты документов.

## Notification Service

- **Responsibility / Owned Data:** отправка подтверждений и результатов возврата; Template, NotificationJob, DeliveryAttempt.
- **API:** `GET /notifications/{id}` (служебный).
- **Dependencies:** события Booking, Passenger для разрешенного получения контакта, внешние провайдеры почты/SMS.
- **Communication:** Kafka и API провайдеров. Событие содержит ссылку на получателя и минимум данных; ошибка отправки не отменяет билет.
- **Scalability:** независимые группы обработчиков по каналу, ограниченные повторы, очередь проблемных сообщений и дедупликация по EventId/каналу.

## Audit Service

- **Responsibility / Owned Data:** неизменяемая история бизнес-операций в отдельном хранилище; AuditEvent.
- **API:** `GET /audit/events?aggregateId=...` (только уполномоченным сотрудникам).
- **Dependencies:** доменные события всех сервисов, включая события изменения расписания, профиля и доставки уведомлений.
- **Communication:** Kafka; запись с EventId, CorrelationId, ActorId, временем, версией и типом операции без лишних персональных данных.
- **Scalability:** пакетная запись, секционирование по времени, архивирование. Уникальность EventId защищает от дублей. Сроки хранения определяются отдельно; Kafka не считается единственным архивом.

Технические логи и метрики собираются платформой наблюдаемости отдельно от Audit. Текущие состояния заказа и минимальные записи идемпотентности остаются в транзакционных БД; долговременная история операций хранится в Audit. Outbox — временный механизм доставки, его опубликованные записи очищаются по политике.

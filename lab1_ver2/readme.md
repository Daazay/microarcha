**Предметная область:** сервис покупки и возврата железнодорожных билетов. [Исходное задание](../LAB1.md).

## Исходные условия и допущения

- Система поддерживает поиск поездов, расписание, выбор мест, бронирование, оплату, возврат, управление пассажирами и уведомления.
- Критические операции должны работать круглосуточно. Числовой SLO, допустимые задержки, RTO и RPO в задании не определены. Доступность 24/7 не трактуется как обещание отсутствия любых отказов.
- 10 000 RPS — заданная нагрузка. Для проектирования считаем ее суммарной внешней нагрузкой; доли чтений и записей неизвестны. Число реплик без измерений не назначаем.
- У значения «10 млн» не указана единица измерения. Оно сохраняется как неопределенное условие и не используется для расчета емкости.
- Рассматривается один оператор с авторитетным учетом мест в нашей системе. Продажа мест, одновременно управляемых внешним перевозчиком, потребовала бы отдельного протокола резервирования.
- Одна покупка охватывает один рейс, возможно несколько мест и пассажиров. Билет с пересадками через несколько рейсов выходит за начальный объем.
- Платежи, идентификация пользователя и доставка почты/SMS выполняются внешними провайдерами. Профиль пассажира и учетная запись пользователя — разные понятия.
- Представленные команды-владельцы — логические зоны ответственности, а не утверждение о наличии пяти отдельных команд в организации.

## 1. Определить основные bounded contexts

**Bounded context** — граница, внутри которой термины, модель данных и бизнес-правила имеют согласованный смысл. Это не папка в проекте и не обязательный отдельный процесс.

| Контекст | Что означает его модель | Ключевые правила |
|---|---|---|
| **Schedule — расписание и описание перевозки** | Станция, маршрут, состав, рейс на дату, остановка, физическое место | Поиск учитывает порядок остановок и дату отправления с выбранной станции; изменение рейса имеет версию. |
| **Sales — продажа билетов** | Заказ, тариф, пассажир, удержание места на участке, билет, запрос возврата | Пересекающиеся участки одного места нельзя продать дважды; билет выпускается после подтвержденной оплаты и закрепления места. |
| **Payment — денежные операции** | Платеж, попытка, подтверждение провайдера, денежный возврат | Повтор команды не вызывает повторное списание; неопределенный ответ провайдера требует сверки. |
| **Notification — коммуникация с клиентом** | Задание на доставку, шаблон, канал, попытка, результат | Сбой доставки не отменяет купленный билет; повторы контролируются отдельно. |
| **Audit — история бизнес-операций** | Событие операции, субъект действия, время, идентификатор сущности | История хранится отдельно от текущего состояния; повторное событие не создает повторную запись. |

Sales — основной бизнес-контекст. Schedule поддерживает продажу; Payment и Notification представляют интеграционные области. Audit — вспомогательный контекст истории, введенный из-за явного требования задания.

**Почему не выделен контекст Search:** в заданной области поиск только читает расписание по станциям и дате. У него пока нет самостоятельной бизнес-модели: это сценарий чтения в Schedule. Усложнение маршрутизации, несколько источников расписания или отдельная команда поиска могут изменить решение.

**Почему учет мест и пассажиры внутри Sales:** в рамках этого варианта они обслуживают продажу билетов. Место в Schedule — элемент физической схемы вагона, а место в Sales — доступность на сегменте конкретного рейса. Passenger в Sales — сохраненные данные путешественника; вход в систему выполняет внешний провайдер идентификации.

## 2. Определить границы микросервисов

Контексты реализуются пятью независимо развертываемыми приложениями. Соответствие «один контекст — один сервис» выбрано для этой архитектуры, а не применяется как универсальное правило.

| Микросервис | Внутренние модули | Что не является отдельным сервисом |
|---|---|---|
| **Schedule** | schedule, journey_search, rolling_stock | Поиск, станции, маршруты, вагоны, физические места. |
| **Sales** | booking, inventory, passengers, checkout | Заказ, билет, учет мест, профиль пассажира, оркестратор покупки. |
| **Payment** | payments, refunds, provider_adapter, reconciliation | Каждая попытка оплаты, адаптер провайдера и сверка. |
| **Notification** | event_consumer, templates, delivery, retries | Отдельные шаблоны и каналы доставки. |
| **Audit** | event_consumer, history_writer, history_query | Запись и чтение истории. |

Пакеты внутри одного приложения вызывают друг друга напрямую через интерфейсы. Между сервисами используются REST API и события. Notification и Audit работают преимущественно как фоновые обработчики, но остаются самостоятельными приложениями с отдельным развертыванием.

Gateway — инфраструктурная точка входа, Kafka — инфраструктура доставки событий. Ни один из них не является bounded context продажи билетов. DevOps — команда, а не микросервис.

## 3. Определить ответственность каждого сервиса

1. **Schedule:** управляет расписанием и схемой поездов, находит рейсы по станциям и дате. Не определяет авторитетный остаток свободных мест.
2. **Sales:** показывает доступность мест, удерживает их, хранит профили пассажиров, рассчитывает цену по тарифу, создает заказ и билет, принимает решение о возврате билета и координирует оплату. Не подтверждает денежную операцию самостоятельно.
3. **Payment:** создает операции у провайдера, принимает и проверяет подтверждения, выполняет денежные возвраты, повторяет безопасные запросы и сверяет неизвестные результаты. Не управляет местами и тарифами.
4. **Notification:** получает факты оформления/возврата, формирует сообщения, доставляет их и учитывает повторы. Не определяет успешность покупки.
5. **Audit:** собирает долговременную историю бизнес-операций и предоставляет ограниченный доступ к ней. Не служит транзакционной БД заказа или заменой мониторинга.

Подробные API и зависимости: [каталог микросервисов](artifacts/service-catalog.md).

## 4. Определить владельца данных каждого сервиса

| Владелец | Собственное хранилище | Авторитетные данные |
|---|---|---|
| Schedule | schedule_db | Station, Route, Train, Carriage, Seat, Trip, TripStop и версии расписания. |
| Sales | sales_db | Booking, Ticket, FareRule, PriceQuote, PassengerProfile, PassengerDocument, Hold, Allocation, SeatSegment, RefundRequest, CheckoutState. |
| Payment | payment_db | Payment, PaymentAttempt, Refund, ProviderEvent. |
| Notification | notification_db | Template, NotificationJob, DeliveryAttempt. |
| Audit | audit_db | AuditEvent — долговременная история операций. |

Владелец данных — соответствующий сервис и ответственная за него доменная команда. DevOps управляет инфраструктурой, резервным копированием и доступами, но не правилами изменения билета или платежа.

БД разделены логически и защищены разными учетными данными. Сервис не обращается к чужим таблицам. В учебном развертывании несколько логических БД могут находиться на одном PostgreSQL; это упрощение инфраструктуры, а не вариант высокой доступности для production.

Внутри Sales модули владеют своими таблицами. Checkout вызывает интерфейсы модулей в рамках общей локальной транзакции для закрепления места и выпуска билета. Прямое произвольное изменение чужих таблиц между модулями не используется.

Копии данных имеют явное назначение: Sales хранит локальную проекцию схемы рейса для учета мест и снимок пассажира в билете. Источник расписания — Schedule; изменяемого профиля — Sales.passengers. Снимок оформленного билета не изменяется вслед за профилем.

Outbox, inbox и записи идемпотентности находятся в БД соответствующих сервисов. Это технические данные доставки и защиты от повторов; они не заменяют отдельное долговременное хранилище Audit.

## 5. Определить основные взаимодействия между сервисами

| Взаимодействие | Способ | Назначение |
|---|---|---|
| Клиент → Gateway → Schedule | HTTPS / REST | Поиск поездов, просмотр расписания и схемы рейса. |
| Клиент → Gateway → Sales | HTTPS / REST | Доступность мест, профили пассажиров, покупка, билет и возврат. |
| Sales → Schedule | REST | Проверка статуса и версии рейса перед бронированием. |
| Sales → Payment | REST | Создание платежа или денежного возврата с устойчивым ключом идемпотентности. |
| Payment ↔ платежный провайдер | HTTPS / подписанный webhook | Создание операции, получение результата, сверка. Webhook проходит через Gateway. |
| Schedule → Kafka → Sales | События | Публикация рейса, изменение и отмена; обновление локальной проекции. |
| Payment → Kafka → Sales | События | Результат платежа/возврата для продолжения процесса. |
| Sales → Kafka → Notification | События | Факт выпуска или возврата билета с идентификатором заказа, без паспортных данных. |
| Notification → Sales | Служебный REST API | Минимальные данные доставки из снимка заказа; ошибка откладывает уведомление, а не покупку. |
| Notification → провайдер почты/SMS | HTTPS | Отправка сообщения. |
| Schedule, Sales, Payment, Notification → Kafka → Audit | События | Отдельное сохранение истории операций. |

**Ключевой сценарий покупки:** Sales создает заказ и временно удерживает места в своей БД → Payment проводит оплату → Sales получает подтверждение → в одной транзакции проверяет удержание, закрепляет места, выпускает билет и записывает исходящее событие. Между удержанием и подтверждением пользовательской оплаты транзакция БД не остается открытой.

Если оплата подтверждена после утраты удержания и место уже недоступно, билет не выпускается; Sales инициирует возврат денег. Объединение Booking и Inventory убирает сетевую границу между ними, но не делает внешнюю оплату частью локальной транзакции.

Подробные шаги, повторы и состояния: [сценарии взаимодействия](artifacts/interactions.md).

## 6. Обосновать выбранную декомпозицию

- **Поиск внутри Schedule:** нужен структурированный запрос «откуда — куда — дата» по данным расписания. Отдельная поисковая БД и ее синхронизация пока не обоснованы. PostgreSQL с подходящими индексами — начальный вариант, который необходимо проверить нагрузкой.
- **Inventory внутри Sales:** занятость места и выпуск билета связаны инвариантом продажи. Одна БД позволяет подтвердить оба изменения атомарно. Это уменьшает число промежуточных распределенных состояний.
- **Пассажиры внутри Sales:** в текущем объеме сохраненные профили используются для покупки. Отдельный сервис добавил бы сетевой вызов и эксплуатационные расходы без показанного независимого сценария.
- **Payment отдельно:** интеграция с провайдером, неизвестные результаты, денежные возвраты и сверка имеют собственные правила и жизненный цикл.
- **Notification отдельно:** внешняя доставка может задерживаться и повторяться независимо от покупки.
- **Audit отдельно:** история изолирована от транзакционных данных и может иметь собственные правила доступа, хранения и архивирования.

Каждая из пяти частей может выпускаться независимо при совместимых контрактах. Цена решения — невозможность независимо развернуть inventory или journey_search без последующего выделения из родительского сервиса. Такая граница осознанно принята до появления измеренной необходимости разделения.

Основное решение зафиксировано в [ADR-001](artifacts/ADR-001.md).

## 7. Привести минимум две альтернативы

| Альтернатива | Преимущества | Недостатки и применимость |
|---|---|---|
| **Модульный монолит с отдельным хранилищем истории** | Проще эксплуатация, локальные вызовы, меньше распределенных состояний. | Все бизнес-модули выпускаются совместно; требование независимого развертывания частей выполняется слабее. Полезен как исходная точка миграции, но не выбран как конечный вариант задания. |
| **Восемь сервисов:** Schedule, Search, Inventory, Booking, Passenger, Payment, Notification, Audit | Независимые релизы и масштабирование поиска, учета мест и профилей. | Больше API, БД, проекций и сетевых отказов. Закрепление места и выпуск билета требуют распределенного процесса. Уместно при разных командах или подтвержденных профилях нагрузки. |
| **Шесть сервисов с отдельным Passenger** при сохранении Search в Schedule и Inventory в Sales | Изолированные доступы к персональным данным, повторное использование профилей несколькими продуктами. | Добавляется зависимость покупки от Passenger и отдельный контракт снимка. Уместно при нескольких каналах/продуктах и самостоятельном владельце профилей. |

Выбран вариант из пяти сервисов: он сохраняет независимые бизнес-области и явно выделенное хранилище истории, но оставляет тесно связанные операции внутри одной транзакционной границы.

## 8. Указать потенциальные проблемы архитектуры

| Проблема | Что предусматриваем | Что остается ограничением |
|---|---|---|
| Конкурентная продажа одного места | Транзакционные блокировки сегментов в фиксированном порядке и проверка занятости; удержание нескольких мест одного рейса атомарно. | Популярный рейс остается точкой конкуренции, даже при большом количестве реплик Sales. |
| Оплата после истечения удержания | Сохраняемый процесс checkout, повторные проверки статуса, компенсирующий возврат. | Некоторое время деньги могут быть списаны без выданного билета. |
| Потеря, дубли и перестановка событий | Outbox, дедупликация в одной транзакции с обработкой, версия агрегата и допустимые переходы. | Нет единого глобального порядка событий или общей транзакции между сервисами. |
| Отказ Kafka | Накопление outbox, мониторинг задержки, повторная публикация после восстановления. | Выпуск оплаченных билетов может задерживаться до получения результата; при исчерпании места в outbox новые операции ограничиваются. |
| Сбой платежного провайдера | Тайм-ауты, устойчивые ключи операций, периодическая сверка, ручной разбор длительных ошибок. | Нельзя достоверно завершить платеж без подтверждения провайдера. |
| Отмена рейса одновременно с покупкой | Проверка версии перед удержанием, обработка TripCancelled, остановка новых продаж после получения отмены и возврат затронутых билетов. | Межсервисная проверка не устраняет окно гонки; строгая мгновенная остановка потребовала бы отдельного согласованного протокола. |
| Устаревшая схема состава | Версионированная проекция; отсутствие нужной версии блокирует бронирование. | Замена состава с проданными билетами требует процесса пересадки/возврата, а не перезаписи занятости. |
| Рост Sales | Модули с явными интерфейсами, мониторинг по операциям, секционирование учета мест по рейсу. | Inventory, пассажиры и заказы пока масштабируются и выпускаются вместе. |
| Нагрузка поиска на Schedule | Индексы, оптимизация запросов, при необходимости read model/реплика чтения/кеш после измерений. | Не доказано достижение 10 000 RPS; выделение Search остается возможной эволюцией. |
| Утечка данных пассажиров | Ограничение доступа, шифрование, снимки только необходимых данных, маскирование логов; в событиях — идентификаторы вместо документов. | Сроки хранения, удаления и правила доступа требуют отдельных требований. |
| Недоступность Sales для Notification | Задание доставки сохраняется и повторяется позже. | Уведомление задержится, но оформленный билет остается действительным. |
| Расхождение истории с текущим состоянием | Надежная доставка, контроль задержки Audit, повторная обработка по EventId, резервное копирование. | История обновляется асинхронно, не одновременно с транзакцией продажи. |
| Общая инфраструктурная точка отказа | Репликация и failover для БД/брокера, резервные копии с проверкой восстановления, несколько экземпляров приложений. | Локальный учебный запуск на одном узле не обеспечивает production-доступность. |

Для проверки проекта нужны нагрузочный профиль, измерения задержек, тест конкурентной продажи, повторная доставка событий, сбой после commit до публикации, поздний платеж и восстановление после отказа. Эти проверки запланированы; реализованной и протестированной системы пока нет.

## Переход от исходного монолита

Сначала закрепляются владельцы данных и внутренние интерфейсы модулей. Затем можно выделить историю и уведомления, расписание и платежи; Sales объединяет оставшуюся транзакционную продажу. Для каждого переноса выполняются миграция, сверка и переключение единственного писателя. Одновременная независимая запись монолита и нового сервиса в одни бизнес-данные не допускается. Конкретный план зависит от схемы и кода исходного монолита, которых в задании нет.

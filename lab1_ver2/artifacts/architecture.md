# Архитектурная схема

[Открыть схему](architecture.svg) · [PlantUML](architecture.puml)

Схема показывает логические контейнеры C4: пять самостоятельных приложений, Gateway, Kafka, пять БД и внешние системы. В подписи приложения перечислены его внутренние модули. Они не развертываются отдельно и не общаются друг с другом через брокер только ради модульности.

## Как читать схему

- Голубые прямоугольники — приложения нашей системы. Gateway маршрутизирует запросы; бизнес-операции принадлежат сервисам.
- Цилиндры — логические БД. SQL-стрелка показывает единственного владельца хранилища.
- Желтый блок — один логический кластер Kafka, а не отдельный брокер на каждый сервис.
- Облака — внешние системы идентификации, оплаты и доставки.
- Сплошные стрелки — запросы/SQL; пунктирные оранжевые — события.

Провайдер идентификации подтверждает учетную запись. PassengerProfile в Sales описывает путешественника; покупатель может оформить билет на другого пассажира. Notification использует снимок контакта покупателя, а не произвольный контакт из изменяемого профиля.

## Хранилища и инфраструктура

Каждый сервис работает со своей БД и миграциями. PostgreSQL выбран как начальная реляционная СУБД для всех пяти хранилищ; один тип СУБД уменьшает разнообразие эксплуатации. Отдельная логическая БД истории удовлетворяет разделению данных; при необходимости audit_db разворачивается на отдельном физическом кластере с собственной политикой хранения.

Kafka выбран для доставки событий нескольким независимым потребителям и повторного чтения. Он не является обязательным требованием задания. RabbitMQ — возможная альтернатива при очередной модели доставки; одновременно оба брокера не вводятся. Outbox находится в БД каждого издателя, а фоновый публикатор — в его приложении. Отдельный сервис для каждого outbox не нужен.

Текущий проект не требует отдельного Search, OpenSearch или Redis. Оптимизации выбираются по результатам измерений. При росте поиска сначала оцениваются запросы/индексы и нагрузка; выделение сервиса — один из вариантов, а не автоматическое следствие 10 000 RPS.

DevOps обеспечивает CI/CD, развертывание, секреты, сбор метрик/логов/трассировок, резервные копии и проверку восстановления. Эти общие платформенные функции не изображены как бизнес-сервисы. В production необходимы избыточность приложений, БД и брокера, согласованные цели восстановления и проверки отказов. Логическая схема не является доказательством высокой доступности.
